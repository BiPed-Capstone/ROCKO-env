## Batch 4: pass speed caps through the supervisor

### Goal and success criteria

A "smaller open item" of the handoff: `max_speed:=`/`max_turn:=` could not reach a mode's teleop node when the
robot runs under the supervisor (`pi/launch.sh robot`, what boots), so a first stand or tethered test could not be
capped short of a hand launch, which cannot be driven (no supervisor, so the teleop never enables). Done when:

1. `pi/launch.sh robot tank_max_speed:=0.3` gives `tank_teleop` the parameter `max_speed` 0.3 (and the same for
   `balance_*`), checked on the mock.
2. With no cap, the child command is exactly what it was.
3. A bad value cannot fail the stack, and cannot make the robot faster than asked: it becomes 0 with an error
   (after review round 1; first written to fall back to the default, see below).
4. A host test covers the command and the refusal, and goes red when either is broken.

### What changed

| File | Change |
| --- | --- |
| `supervisor/modes.py` | `CAP_ARGS`, `cap_problem(text)` (empty is fine; not a number, or outside [0, 1], or NaN, is refused), `checked_caps(texts)` (a refused value becomes "0") and `launch_command(mode, mock, log_root, caps)`, which builds the child's `ros2 launch` command; plain Python, so the host test can import it |
| `supervisor/Supervisor.py` | parameters `tank_max_speed`, `tank_max_turn`, `balance_max_speed`, `balance_max_turn` (text, default empty); `read_caps()` logs each refused value; `start_stack()` uses `launch_command()`; the now unused `PACKAGE` constant removed |
| `bringup/launch/rocko_robot.launch.py` | the four launch arguments, passed to the supervisor |
| `tools/supervisor_state_machine_test.py` | `test_speed_caps_reach_the_mode_launch` (also checks that both mode launches declare the caps, or a passed one would be silently ignored) and `test_bad_caps_are_refused` |
| docs | `robot-supervisor.md` (a *Speed caps* paragraph; its "nothing has run on the Pi" list replaced by what has), `drive-with-usb-controller.md` (first drive with a cap; the gap removed), the handoff's open item removed |

Why text and not a float parameter: an empty value has to mean "not set, use the launch's default", and the
defaults differ per mode (tank 1.0 / 1.0, balance 0.05 / 0.2); repeating them in the supervisor would make two
homes for each number.

## Batch 6: a Tier 0 check that every hardware plugin name can be found

### Goal and success criteria

Off the Pi the real hardware plugins (`rocko_env/Motor12VoltQuadEncoder`, `rocko_env/ICM20948`) are never loaded:
the mock or the simulator stands in for them. So if the name in a xacro, the `<class name>` in
`rocko_env_hardware.xml` and the `PLUGINLIB_EXPORT_CLASS` in the C++ source stopped agreeing, every off-Pi tier
would stay green and the robot would fail to start ("class not found"). Next-steps row 1.6 (rename `ICM20948` to
the BNO055) is blocked on exactly that risk. Done when `verify_urdf.sh` fails, naming the plugin, for each of: a
renamed XML class, a changed exported base class, a misspelt plugin in a xacro; and passes on the tree as it is.

### What changed

| File | Change |
| --- | --- |
| `tools/check_plugin_names.py` (new) | Standard library only. For every `<plugin>` in the expanded URDFs it is given: the name must be a `<class name>` in `rocko_env_hardware.xml`, that class's `type` must be exported by a `PLUGINLIB_EXPORT_CLASS(type, base)` in some `.cpp` under `rocko_env/rocko_env`, with the XML's `base_class_type`, and from a `.cpp` that `CMakeLists.txt` builds; the XML's `<library path>` must be the `add_library` target, and CMake must export the XML for `hardware_interface`. Comments (C++ and CMake) are removed before matching. `mock_components/GenericSystem` (ros2_control's own) is accepted by name |
| `verify_urdf.sh` | runs it on all seven expansions; header and PASS line say so |
